# ECS Audit: Findings & Cleanup Plan

## Findings

### 1. Pervasive Direct Mutation (Critical)

`getComponent` returns a live reference to the stored object, and callers mutate it in-place everywhere. The two patterns are mixed inconsistently:

|**Correct**|**Direct mutation (wrong)**|
|---|---|
|`combat.ts`: `world.addComponent(id, Health, { ...h, current: newVal })`|`movement.ts`: `pos.x = targetX`|
|`turn-manager.ts`: `world.addComponent(id, Energy, updated)`|`ai.ts`: `playerHealth.current -= damage`|
||`shell-stats.ts`: `health.max = shell.maxHealth; defense.armor = shell.armor`|
||`software-effects.ts`: `health.current = Math.min(...)`|
||`stability.ts`: `health.current = Math.max(...)`|
||`item-pickup.ts`: `health.current += effect.value`|
||`ai.ts`, `pack-coordinator.ts`, `software-effects.ts`: `statusEffects.effects.push(...)`|
||`ai.ts`, `firmware.ts`, `pipeline.ts`: `pos.x = ...; pos.y = ...`|

Mutations that bypass `addComponent` are invisible to the store—they don't trigger `COMPONENT_ADDED`, they break serialization snapshots, and they make state changes untraceable.

### 2. Bug: ai.ts Logic-Leaker death sets isAlive = true instead of false

`playerHealth.isAlive = true` at line ~407 in `ai.ts`. The player is marked alive when they should be dead.

### 3. System-to-System Hard References

Three systems hold direct references to other systems at construction time:

- `createAISystem(... movementSystem, deadZoneSystem)` — AI calls `movementSystem.processMove()` and `deadZoneSystem.createDeadZone()` directly.
    
- `createFirmwareSystem(... movementSystem, heatSystem)` — Firmware calls `movementSystem.processMove()` and `heatSystem.ventHeat()`.
    
- `createAugmentSystem(... statusEffectSystem, heatSystem)` and `createKernelPanicSystem(... statusEffectSystem)` — Same pattern.
    

This means systems can't be initialized independently, can't be tested in isolation, and the engine-factory becomes the glue holding it all together rather than the event bus.

### 4. RunInventoryRegistry Global Singleton (Architectural)

`run-inventory.ts` exports a module-level singleton via a global namespace hack. It's touched directly in: `item-pickup.ts`, `run-ender.ts`, `sync-bridge.ts`, `pipeline.ts`, and `setup.ts`. This:

- Breaks the "pure function" contract of `runActionPipeline` in `pipeline.ts` (the pipeline mutates the singleton as a side effect).
    
- Means run inventory state isn't in the ECS world, so it doesn't serialize/deserialize automatically.
    
- Requires manual sync (`RUN_INVENTORY_SYNCED` event + a `TODO: HACK` comment in `setup.ts`).
    

### 5. Duplicate Combat Logic in pipeline.ts

`setupInternalHandlers` in `pipeline.ts` re-implements `BUMP_ATTACK` → damage → death logic that already lives in `combat.ts`. Both paths import `resolveDamage`/`collectDamageModifiers`, but `pipeline.ts` uses direct mutation (`defenderHealth.current = ...`) while `combat.ts` uses the correct `world.addComponent` path.

### 6. Phase enum / registerSystem are Dead Code

World has `registerSystem(phase, fn)` and `executeSystems(phase)` methods with a `Phase` enum. Zero systems are actually registered this way—all systems are wired manually in `engine-factory.ts` and called explicitly in `turn-manager.ts`.

### 7. Deprecated Scrap Component Still Active

`Scrap` is marked `@deprecated` with a comment pointing to `CurrencyItem`. `item-pickup.ts` still has a live code path reading `Scrap` from entities and mutating `playerScrap.amount += ...` directly.

## Cleanup Plan

### Phase 1 — Bug Fix (standalone, do now)

- `ai.ts`: Fix `playerHealth.isAlive = true` → `false` in the Logic-Leaker kill path.

> [!NOTE]
> We need to further evaluate how death is determined. It's likely incorrect for random systems (like AI) to determine entity lifespans. This should be consolidated or handled by a central authoritative system.
    

### Phase 2 — World API Hardening (foundation)

- Add `world.patchComponent<T>(id, def, patch: Partial<T>): void` as a convenience wrapper over `addComponent`.
    
- Change `getComponent<T>` return type to `Readonly<T> | undefined` to surface direct-mutation sites as TypeScript errors.
    

### Phase 3 — Eliminate Direct Mutations

1. **Position writes**: Use `world.patchComponent(id, Position, { x: targetX, y: targetY })`.
    
2. **Health writes**: Use `world.patchComponent(id, Health, { current: newVal })`.
    
3. **Shell Stats**: Replace direct field mutation for `Health`, `Defense`, `Energy`.
    
4. **Arrays**: `StatusEffects` push → `world.patchComponent(id, StatusEffects, { effects: [...existing, newEffect] })`.
    
5. **Scrap**: Migrate to `CurrencyItem` path.
    

### Phase 4 — Decouple System-to-System References

Replace injected system references with new events on `GameplayEvents`:

- `MOVE_REQUESTED { entityId, dx, dy }`
    
- `CREATE_DEAD_ZONE { x, y, duration, damagePerTick, creatorId }`
    
- `VENT_HEAT_REQUESTED { entityId }`
    
- `APPLY_STATUS_EFFECT { entityId, effect }`
    

### Phase 5 — Migrate RunInventoryRegistry to ECS

- Define new player components: `RunCurrency { stacks: CurrencyStack[] }` and `RunInventory { items: RunInventoryItem[] }`.
    
- Stamp these onto the player entity at game start.
    
- Remove the singleton and global namespace hack.
    

### Phase 6 — Cleanup & Architectural Refactor

> [!NOTE]
> See docs/ENGINE_GUIDELINES.md for the full architectural vision for this phase. This section is a summary of that document, but the full document should be considered the primary source of truth for Phase 6.

The core objective of this phase is to move the architecture from a fragile reactive event mesh into a highly predictable, tick-based simulation state machine. We will utilize the ECS `registerSystem` capability combined with **Intent Components**, keeping the `EventBus` strictly for cross-domain boundaries (UI, Network, Analytics).

**Step 6.1: Remove deprecated `Scrap` component**
- **Findings:** The `Scrap` component has been superseded by the `CurrencyItem` pattern, but there are still dangling references to it (e.g., in `src/shared/components/scrap.ts` and entity templates).
- **Approach:**
  - Delete the `Scrap` component definition and schema.
  - Scrub the codebase for any remaining queries or `patchComponent` calls targeting `Scrap` and migrate them to use `CurrencyItem` and `InventoryUtil`.
  - Update `.json` template definitions (like `economy.json` or `scrap.json`) to ensure nothing spawns with the deprecated component.

**Step 6.2: Migrate core systems (Movement, Combat) to `registerSystem` (Phase-Driven Intent Pattern)**
- **Findings:** `registerSystem` is currently only used as an afterthought in `engine-factory.ts` for `Phase.POST_TURN`. Every other system is manually wired and driven by the `EventBus` (e.g., `MOVE_REQUESTED` -> `ENTITY_MOVED` -> `BUMP_ATTACK`). This creates unpredictable execution orders and breaks state prediction.
- **Approach:**
  - Keep and heavily utilize `registerSystem`.
  - Expand the `Phase` enum in `src/engine/ecs/types.ts` to fully model the turn lifecycle (`PRE_TURN`, `GATHER_INTENT`, `ACTION`, `REACTION`, `CLEANUP`, `POST_TURN`, `RENDER`).
  - Modify `TurnManager` to execute the phases in sequence via `world.executeSystems(Phase.X)` during `executeTurnCycle()`.
  - Introduce **Intent Components** (`MoveIntent`, `AttackIntent`). Instead of emitting `MOVE_REQUESTED`, inputs and AI attach a `MoveIntent` to the actor.
  - Refactor Movement to an `update(world, grid)` function registered to `Phase.ACTION` that queries `MoveIntent`.
  - Refactor Combat to an `update(world, grid)` function registered to `Phase.REACTION` that queries `AttackIntent`.
  - Ensure core systems only *emit* events (`MESSAGE_EMITTED`, `ENTITY_DIED`) to signal external UI/logging layers, never to drive internal game logic.

**Step 6.3: Collapse `pipeline.ts` duplicate combat path**
- **Findings:** Because `pipeline.ts` runs a simulation on a cloned `World` instance, it currently completely duplicates the `BUMP_ATTACK` -> `DAMAGE_DEALT` -> Death logic inside `setupInternalHandlers`.
- **Approach:**
  - Extract a `registerCoreSystems(world, grid)` helper function. Both `engine-factory.ts` and `pipeline.ts` will call this to register the exact same pure system functions.
  - Inside `pipeline.ts`, delete `setupInternalHandlers` entirely.
  - Instead of manually resolving damage, `pipeline.ts` will simply attach an `AttackIntent` to the simulated entity and call `clonedWorld.executeSystems(Phase.ACTION)`. The exact same combat logic will execute authoritatively with zero code duplication.

**Step 6.4: Migrate Movement-Reactive Systems (Batch A)**
- **Findings:** Systems like `item-pickup.ts`, `anchor-interaction.ts`, and `pack-coordinator.ts` currently listen to `ENTITY_MOVED`.
- **Approach:** 
  - `MovementSystem` attaches a `MovedThisTurn` tag to entities that successfully change coordinates.
  - Convert reactive systems into `update()` functions registered to `Phase.REACTION` or a new `Phase.INTERACTION`. They query `MovedThisTurn` to check new coordinates.
  - A system in `Phase.CLEANUP` removes all `MovedThisTurn` tags.

**Step 6.5: Migrate Death & Destruction Systems (Batch B)**
- **Findings:** `currency-drop.ts` and `run-ender.ts` listen to `ENTITY_DIED` because `combat.ts` instantly destroys the entity, taking its components with it.
- **Approach:** 
  - `CombatSystem` stops calling `world.destroyEntity()`. Instead, it attaches a `Dying` component if health <= 0.
  - `currency-drop.ts` and `run-ender.ts` register to `Phase.CLEANUP`, querying `(Actor, Dying)` to spawn loot or trigger game-overs.
  - A final `GravediggerSystem` runs at the very end of `Phase.CLEANUP` to actually call `world.destroyEntity()`.

**Step 6.6: Migrate Resource & Environmental Systems (Batch C)**
- **Findings:** `heat.ts`, `kernel-panic.ts`, `stability.ts`, and `dead-zone.ts` rely on event signals (`VENT_HEAT_REQUESTED`, `HEAT_CHANGED`, `PLAYER_ACTION`, `CREATE_DEAD_ZONE`).
- **Approach:** 
  - Register `heat.ts` and `stability.ts` to `Phase.PRE_TURN` and `Phase.ACTION` to naturally decay/accumulate resources. Convert requests to Intents (e.g., `VentIntent`).
  - Register `kernel-panic.ts` to `Phase.CLEANUP` to query `Heat` directly instead of listening for changes.
  - Have AI systems directly spawn dead zone entities using `EntityFactory` instead of emitting `CREATE_DEAD_ZONE`.

**Step 6.7: Migrate Complex/Conditional Logic (Batch D)**
- **Findings:** `augment.ts` listens to a wide array of combat and action events (`DAMAGE_DEALT`, `FIRMWARE_ACTIVATED`, `ENTITY_DIED`).
- **Approach:** 
  - Migrate "On Kill" augments to run in `Phase.REACTION` querying entities with the `Dying` component.
  - Migrate "On Damage" augments to integrate directly into the pure `resolveDamage` pipeline as `DamageModifiers`.

**Step 6.8: Event Definition Cleanup (The "Ultra Clean" State)**
- **Findings:** After executing Steps 6.2 through 6.7, a specific set of events in `GameplayEvents` (`src/shared/events/types.ts`) will be completely orphaned. These events were historically used as "commands" between internal systems, which violates the Phase-Driven Intent pattern.
- **Approach:** Delete the following event definitions entirely. If any TypeScript errors arise, it indicates a system was missed in the migration batches:
  1. `MOVE_REQUESTED`: Replaced by `MoveIntent`.
  2. `BUMP_ATTACK`: Replaced by `AttackIntent`.
  3. `CREATE_DEAD_ZONE`: Replaced by direct `EntityFactory.create()` usage during `Phase.ACTION`.
  4. `VENT_HEAT_REQUESTED`: Replaced by `VentIntent`.
  5. `ADD_HEAT_REQUESTED`: Replaced by direct `world.patchComponent` calls.
  6. `APPLY_STATUS_EFFECT`: Replaced by direct `world.patchComponent` calls.
  7. `STABILITY_ZERO`: Replaced by `Phase.CLEANUP` logic inside `run-ender.ts` querying the `Stability` component directly.

*Note on remaining events:* Events like `ENTITY_MOVED`, `DAMAGE_DEALT`, `HEAT_CHANGED`, and `ENTITY_DIED` will **remain** in the codebase. However, they will be strictly relegated to their intended purpose: signaling external domains (the PixiJS renderer, the UI layer, and the audio system). No internal `src/game/systems/*.ts` file should ever use `eventBus.on()` to listen to them.

**Step 6.9: Documentation & Anti-Pattern Scrub**
- **Findings:** Throughout the iterative development of the codebase, many comments, `TODO`s, and JSDoc strings were written that reference old event-driven patterns, manual system-to-system function calls, or direct state mutation.
- **Approach:**
  - Execute a comprehensive search for outdated architectural comments (e.g., references to "emitting `BUMP_ATTACK`", "listening for `MOVE_REQUESTED`", "manually resolving damage", or "bypassing the store").
  - Delete or update these comments to correctly describe the new Phase-Driven Intent Pattern.
  - Review `engine-factory.ts` and `turn-manager.ts` to ensure all system initialization and state loop comments accurately describe their phase registrations.
  - Ensure no misleading "HACK" or "TODO" comments remain regarding execution order, as the Phase structure permanently solves this.
  - Verify that `docs/ENGINE_GUIDELINES.md` is strictly adhered to and that no lingering code violates its documented anti-patterns.

---

Rough sequencing note: Phases 1 and 2 are independent and low-risk. Phase 3 follows directly and is mostly mechanical once the TS errors are visible. Phases 4 and 5 are the bigger behavioral changes. Phase 6 is a significant architectural refactor and must be executed in strict order: 6.1 (Scrap removal), 6.2 (Core Intents), 6.3 (Pipeline Collapse), 6.4-6.8 (Batch Migrations and Event Deletion), and finally 6.9 (Documentation Scrub) to guarantee an ultra-clean, unambiguous foundation for all future AI development.
